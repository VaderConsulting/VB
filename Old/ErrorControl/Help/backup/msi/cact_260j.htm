Microsoft Windows Installer

Nested Installation Actions

Nested installations are not available with Windows Installer version 1.0.

A nested installation action installs another Windows Installer package during a currently running installation. A nested installation is added to a package by authoring a nested installation action into the CustomAction table and scheduling this custom action into the sequence tables. The Target field of the CustomAction table contains a string of public property settings used by the nested installation. The Source field of the CustomAction table identifies the nested package.

The type of nested installation action is specified in the Type field of the CustomAction table. Depending upon the custom action type, the package for the nested application can reside in a sub-storage of the main package, as a file at a location specified by a property, or as an advertised application on the user's machine. The following types of custom actions perform a nested installation.

Custom action type Description
Custom Action Type 7 Nested installation of a product residing in the installation package.
Custom Action Type 23 Nested installation of an installer package within the current source tree.
Custom Action Type 39 Nested installation of an advertised installer package.

A nested installation shares the same user interface and logging settings as the main installation.

The use of deferred execution with nested installation actions is unnecessary because the installer combines rollback information from the nested and main installations. This means that all changes are reversed upon a rollback installation.

The return values for nested installation actions are the same as for other custom actions. See Custom Action Return Values.

Standard or custom actions that specify an automatic reboot of the system, or request the user to reboot, can also perform reboot or request from within a nested installation.

Once the installer begins a nested installation, it locks out all other all other installations until the nested installation is complete and before continuing the main installation. The installer can only execute nested installations as synchronous custom actions. See Synchronous and Asynchronous Custom Actions. The option flags described in Custom Action Return Processing Options must be set to none (+0) or msidbCustomActionTypeContinue (+64).

A nested installation action can install an application to be run locally, to run from source, to be reinstalled, or to be removed in the same manner as when using MsiInstallProduct for a regular installation. To specify the type of installation, pass either the ADDLOCAL, ADDSOURCE, REINSTALL, or REMOVE property to the nested installation action.

There is no method for querying a package for its cost. This makes the costing of a nested installations difficult. Rows must be added to the ReserveCost table to indicate the folders and worst-case costs of the component associated with the nested install.

The only Custom Action Return Processing Options available with nested installation actions are none (+0) or msidbCustomActionTypeContinue (+64).

Note that a parent installation cannot call its own package as a nested installation action.

Note that if a per-machine installation attempts to run a per-user nested installation, the installer registers the parent installation as per-user by default. This can cause the installer to incorrectly remove the application because the installer attempts to uninstall the application per-machine when it is actually registered as per-user. To force the state of a nested installation to track the state of its parent installation, enter ALLUSERS=[ALLUSERS] in the Target column of the CustomAction table. In this case, the nested installation is per-machine if the parent is per-machine, and the nested installation is per-user if the parent is per-user.

Developers should note the following warnings when authoring nested installations.

  • Parent and child installations of nested installations cannot share components:
  • An administrative installation cannot also contain a nested installation.
  • Patching and upgrading may not work with nested installations.
  • The installer may not properly cost a nested installation.
  • Integrated progress bars cannot be used with nested installations.
  • Resources that are to be advertised cannot be installed by the child of a nested installation.
